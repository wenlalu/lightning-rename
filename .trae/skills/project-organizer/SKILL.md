# Project Organizer（项目工程化整理师）

将任意状态的软件项目（未开始 / 半成品 / 已完成但混乱）治理为**规范、统一、可维护**的形态。融合 grill-me 面试式方法：动手前先问清关键事实，动手中遇异常立即停下核实，绝不凭记忆或推断下结论。

---

## 0. 核心原则（红线，任何场景都适用）

1. **仓库根 = 项目根**：个人开发者主流实践，所有文件围绕 Git 仓库根组织，而非按"阶段编号文件夹"分类。
2. **逐字节一致性红线**：项目若已有 Git 远程，被跟踪文件必须与远程 blob **逐字节一致**（用 `git hash-object` 比对，不凭记忆）。允许的偏差只有一种：明确记录在变更清单里的有意修改。
3. **删除前必须验证**：哈希聚类 + 时间戳 + 内容比对三重判定新旧；不确定就先问用户，绝不先删后看。
4. **意外不一致 → 立即停止**：发现比对结果与预期不符时，停止后续操作，如实报告差异（精确到字节/行），等用户裁决。
5. **权威产物不可重建替代**：编译产物哈希不可复现（PE 时间戳等），权威发布产物只能从官方 Release 资产恢复并做 SHA-256 校验。
6. **高危动作先探测后执行**：含中文路径的脚本经 `powershell -File` 执行前确认 UTF-8 BOM，否则会产生乱码目录（GBK 误解码）。

## 1. 标准项目目录结构

```
<repo-root>/                          ← 仓库根 = 项目根
├─ .git/                              ← 本地仓库（origin 指向远程）
├─ .gitignore                         ← 忽略构建产物/本地归档
├─ .gitattributes                     ← 行尾与二进制策略（见 §2）
├─ .editorconfig                      ← 编辑器行为统一
├─ LICENSE
├─ README.md                          ← 含构建/运行/测试三条命令
├─ CHANGELOG.md                       ← 语义化版本记录
├─ <ProjectName>/  或 src/            ← 源码（每语言按其惯例）
├─ tests/                             ← 自动化测试 + 测试夹具
├─ docs/                              ← 规范、审查报告、教程
├─ build.ps1 / Makefile / ...         ← 一键构建入口
├─ dist/ 或 release/ 或 发布版/       ← 构建产物归档（gitignored）
└─ tools/                             ← 本地环境工具（gitignored，绝不入库）
```

**要点**
- 解决方案文件（`.sln` 等）放仓库根，其相对引用天然有效。
- 构建脚本输出目录与 README 描述**必须一致**（文档-代码-目录三方一致）。
- 大体积本地文件（安装器、数据库、媒体）一律 `tools/` 或归档目录 + gitignore。

## 2. 代码组织与命名规范

| 项 | 规范 |
|---|---|
| 目录/源码文件名 | 英文，PascalCase 或全小写连字符；**禁用中文**（面向最终用户的发布产物名可中文） |
| 单文件职责 | 一类一文件；超过约 500 行或承担 3 种以上职责时拆分 |
| 编码 | UTF-8 **无 BOM**（除非运行环境强制 BOM，如 PowerShell 5.1 下的中文脚本） |
| 行尾 | 新项目全仓库统一一种；**既有仓库先冻结**（`.gitattributes` 写 `* -text`）保逐字节一致，择机做一次专门的规范化提交 |
| 重复 | 同一内容文件全仓库只保留一份规范副本，其余以哈希证明重复后删除 |
| 产物 | 编译产物不进版本库；发布产物归档并附 SHA-256 |

`.gitattributes` 基线（冻结行尾 + 二进制声明）：
```
* -text
*.png binary
*.jpg binary
*.exe binary
*.ico binary
```

`.editorconfig` 基线：
```
root = true
[*]
charset = utf-8
insert_final_newline = false
trim_trailing_whitespace = false
[*.cs]
indent_style = space
indent_size = 4
```

## 3. 文档与配置要求

**必备六件套**：`README.md`、`LICENSE`、`CHANGELOG.md`、`.gitignore`、`.gitattributes`、`.editorconfig`。

- README 至少含：项目一句话简介、运行环境、**构建命令、运行命令、测试命令**（三条命令必须实测通过）、许可证。
- CHANGELOG 按版本记录：新增/修复/兼容性/质量保障，发布产物附 SHA-256。
- 文档里写的每个路径、每条命令都要与实际一致；发现不符，**修文档或修代码其一**，不许两头不一致。

## 4. 版本迭代流程

```
代码评审 → 测试全绿 → 构建 → 版本号(Major.Minor.Patch) → CHANGELOG 更新
→ git tag vX.Y.Z → Release 上传资产 + 公布 SHA-256 → Pre-release 观察期
→ 无问题转 Latest → 保留上一版本 Release 可回滚 → 收集反馈进入下一迭代
```

- 每次变更前问：能回滚吗？有审计记录吗？
- 本地仓库与远程同步：`git fetch` → 比对 → 提交 → 推送；禁止 force push 破坏历史。

## 5. 场景 A：整理混乱项目（核心流程，五步法）

**第一步 全量扫描**：递归列出全部文件（路径/大小/修改时间），再对疑似副本做哈希聚类。

**第二步 版本判定**：
- 哈希相同 = 同一文件的多份副本 → 只留一份规范副本；
- 哈希不同但同名/同源 → 用时间戳 + 远程 blob + 内容差异判定新旧；
- 编译产物以"是否等于官方发布的 SHA-256"判定权威性，不以时间新旧判定。

**第三步 面试式询问（grill-me 融合点）**——动手前必问，一次问清：
1. 源码完整吗？有没有更完整或更详细的版本？
2. 哪个是权威/最新版本？判断依据是什么？
3. 有 Git 远程仓库吗？整理后需要与远程逐字节一致吗？
4. 哪些旧文件确认可以删？删除是不可逆的，需要你逐项确认。
5. 有没有必须保留的外部依赖（安装包、许可证文件）？

> **源码不完整的处理**：先问用户是否有完整源码；若用户回答没有，则自行解析该软件——读代码理清结构、尝试构建、必要时反编译或重写缺失部分——补齐后再按本 skill 规范整理，并如实标注哪些是补齐/重建的。

**第四步 先移动、后删除**：
- 先把保留文件迁入标准结构（移动不破坏内容）；
- 修复路径引用（sln/构建脚本/文档），**实测构建与测试**；
- 最后才执行删除，且每项删除都有已验证的依据；
- 遇到编码乱码目录（如 `鍙戝竷` 类 GBK 乱码名）：确认为空/无效后删除。

**第五步 验证与产出**：
- 逐字节验证（git blob 比对）通过才收尾；
- 输出**变更清单**（保留了什么、删除了什么、每项依据）；
- 输出**10 条分级改进建议**（见 §8）。

**实战陷阱速查**（整理既有项目时逐条自查）：
- `core.autocrlf=true` 会在克隆/检出时静默转换行尾 → 一切比对以 `git ls-tree` 的 blob 哈希为准；
- 从别人克隆的工作区复制文件 ≠ 复制远程内容（行尾可能已被转换）→ 直接 `cat-file blob` 取字节流；
- 无 BOM 的中文脚本经 PowerShell 5.1 `powershell -File` 执行 → 乱码路径 → 先加 BOM；
- "看起来一样"不算数，`Get-FileHash` / `git hash-object` 说了才算。

## 6. 场景 B：从零创建新软件

1. 先问清（grill）：目标平台、语言栈、目标用户、是否开源、命名。
2. 按标准目录结构（§1）一次性搭好骨架 + 六件套配置（§3）。
3. 第一天就 `git init` 并建远程，第一个提交即规范结构本身。
4. 开发全程持续遵循：每次提交前自查——新增文件是否在正确目录？命名合规？文档命令仍有效？产物未入库？
5. 每完成一个功能即写测试，测试不全绿不进入下一个功能。

---

## 7. 场景 C：迭代半成品软件

1. 先做场景 A 的第一、二步（扫描 + 判定现状），搞清"已有什么、缺什么"。
2. 补齐缺失部分：结构缺口（tests/docs/配置）、质量缺口（构建脚本、CI）、文档缺口。
3. **新增内容必须与既有代码风格组织一致**：行尾跟随现有约定、命名跟随现有大小写风格、目录跟随现有层级逻辑——先模仿后统一，不引入第二种风格。
4. 每轮迭代走 §4 版本流程，CHANGELOG 记录每次增量。

---

## 8. 场景 D：产出 10 条改进建议

每次整理完成后必做。依据两条线：
- **源码质量**：规范性（结构/命名/注释）、正确性（潜在 bug）、重复冗余；
- **测试情况**：覆盖率、自动化程度、性能基线。

输出格式：**恰好 10 条**，标注三级优先级：

```
高（立即做，影响正确性/一致性/发布）
1. ...
2. ...
3. ...
中（近期做，影响可维护性/可信度）
4. ...
中/低...
低（择机做，锦上添花）
10. ...
```

每条必须给出**可执行的具体动作**（改哪个文件、跑什么命令），不许空泛。

---

## 9. 输出模板（每次整理后交付）

```markdown
# 项目整理报告
## 一、发现的问题（严重性分级表）
## 二、结构变更（旧→新映射 + 理由）
## 三、逐项修复明细（修改/理由）
## 四、验证结果（逐字节比对 / 构建 / 测试，全部实测）
## 五、10 条改进建议（高/中/低）
## 六、最终目录结构
```

## 10. 自我完善条款

整理过程中遇到本 skill 未覆盖的新情况、并形成了可复用的新规范（新陷阱、新验证手段、新结构约定）时，将其沉淀回本 SKILL.md 对应章节，使 skill 持续进化。新增内容须是**可复用的通用规则**，不得包含具体用户的路径、仓库地址、凭据或一次性任务数据。
